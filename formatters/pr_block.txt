# This event: merged pull request

A merged pull request is a completed unit of work. Unlike a single push, it represents a feature, fix, or change that has been finished, reviewed, and landed on the main branch. The story you are telling is the story of something that is now done.

## Working from the developer's description

The `body` field contains the developer's own explanation of their work.

**When the description is substantive:** treat it as your primary source and your guide for tone and structure. Reframe it for a social audience — keep the developer's voice, message, and emphasis intact. The only changes you should make are (a) clarifying technical terms for non-technical readers, and (b) restructuring so it reads naturally as a social media post rather than as a technical PR description. Do not add bells and whistles. Do not change what the work is or inflate its significance.

**When the description reads "No description provided" or is vague:** work from the title and the scale signals instead. Write less. Do not compensate for missing information by inventing it.

## Reading the title

The title usually establishes what kind of work this was. Many developers use conventional prefixes — `feat:` (new feature), `fix:` (bug fix), `refactor:` (restructuring without behavior change), `docs:`, `chore:`, `perf:` (performance). Use these to identify the nature of the work and reflect it accurately.

If the title is vague or unprefixed, infer the nature of the work from the input as a whole. If you still cannot determine it confidently, describe what happened plainly rather than guessing at a category.

## Scale signals — internal only

This event provides commit count, lines added, lines deleted, and files changed. **Never state these numbers in the output.** They exist only to calibrate how much post the work justifies:

- Small (few commits, small line counts, 1–2 files): 2–3 sentence body
- Medium: 3–5 sentences
- Large (many commits, substantial line counts, many files): up to 7 sentences, still concise

## Evidence for Stack and Concepts

For this event, both Stack and Concepts are drawn from the `title` and `body` only — the developer's own words. There are no file names or extensions available in a pull request payload, so there is nothing to infer a technology from beyond what the developer explicitly wrote.

## GitHub link

`Check out my project: github.com/[repo]`

# Context

You will receive:
- `title` — the developer's PR title
- `body` — the developer's PR description, or "No description provided"
- `commits` — number of commits (internal signal only)
- `additions` — lines added (internal signal only)
- `deletions` — lines removed (internal signal only)
- `changed_files` — number of files changed (internal signal only)
- `username` — the developer's GitHub username (for the link only)
- `repo` — owner/repo, e.g. `betancourt-ncs/gitbrief` (for the link only)

🔐 I just implemented unique authentication verification in my gitbrief project!

Each user now gets their own authenticated signing secret when they're set up, rather than sharing one global key across the whole system. Basically, when the trigger (a webhook) arrives, the server first identifies which user it belongs to, then verifies the request signature against that specific user's signing secret, confirming the request is authentic before anything else runs. The practical difference is the blast radius: if one user's secret is ever exposed, it affects only them and not the rest of the userbase.

With per-user authentication in place, a compromised credential can no longer be used to send forged requests on behalf of any other user, substantially improving my app's security.
