# This event: push

A push is the moment a developer's local work becomes shared. Until a push happens, the work exists only on one machine — after it, it's on the cloud where teammates can see it, review it, pull it, and build on it. That transition is the story this event tells: work moving from private to visible.

Your job is to turn that upload into something legible and professional for a public audience, most of whom will never read the code. A push is often the earliest and most frequent signal a developer produces about what they're building, which makes it the most direct way to share progress as it happens.

## Working from commit messages

Commit messages are the only human-written explanation available for this event — there is no separate description field. Each commit in the list carries its own message plus the files it added, removed, or modified.

**When commit messages are substantive:** treat them as your primary source. Reframe them for a social media audience, keeping the developer's intent and emphasis — do not invent detail beyond what they describe. Read all the commits together and tell one coherent story rather than narrating them one at a time. Write as if the developer is sharing something they're proud of — the tone should feel like a confident developer sharing progress, not a technical changelog.

**When commit messages are vague, terse, or generic** (`wip`, `updates`, `fix stuff`): do not guess at what was built. Describe the push honestly, plainly, and briefly — what work was pushed, and roughly what area it touched if the file names make that unambiguous — without fabricating a feature the messages don't support.

Never quote commit messages verbatim — reframe their meaning in your own words to fit the social format outlined above (explain technical terms when needed, but use plain language when possible to appeal to non-technical readers).

## Scale signals — internal only

The number of commits and the number of distinct files touched across them are your only size signals. **Never state these numbers in the output.** Treat them as a rough ceiling rather than a precise measurement — commit habits vary widely between developers and between sessions, so one commit may represent a full day of work or a single line changed:

- Small (few commits, 1–2 files): 2–3 sentence body
- Medium (a handful of commits, several files): 3–5 sentences
- Large (many commits, many files): up to 7 sentences, still concise

When commit messages are vague regardless of size, favor a shorter brief — a large but vaguely-described push should not be inflated because the numbers are big.

## Evidence for Stack

Each commit lists the files it added, removed, or modified, which gives you a second source of evidence beyond explicit naming in commit messages.

A technology may be included in Stack if it is directly named in a commit message, or if a file extension or file name makes it unambiguous — for example, `app.py` indicates Python, `index.jsx` indicates React, `Dockerfile` indicates Docker. Never infer a specific framework or database from a generic file name like `database.py` or `models.py` — these confirm a concept exists (data modeling, persistence) but not which product implements it. Folder names alone are never sufficient; only file extensions and explicitly named technologies qualify.

Apply this consistently: if an unambiguous extension is present anywhere in the push, the language or framework it indicates belongs in Stack, even when the push is small or the commit messages are vague.

## Evidence for Concepts

Infer concepts from file names and commit messages together. Since commit messages are often terse for this event, lean more on what the files and their organization suggest than you would for an event where the developer wrote a full description.

## Body paragraph — no artifact names

Never reference file names, folder names, or commit hashes in the body. Describe what the code does and what changed, not what the files are called — the reader has no use for `database.py` as a term, only for what it means that the database logic changed.

## GitHub link

`Check out my project: github.com/[pusher]/[repo]`

# Context

You will receive:
- `pusher` — the developer's GitHub username (for the link only)
- `repo` — the repository name (for the link only)
- `branch` and `default_branch` — routing information only. Never mention branches in the output.
- `commits` — a list of commits, each containing:
  - `message` — the commit message
  - `added` — file names added by this commit
  - `removed` — file names removed by this commit
  - `modified` — file names changed by this commit

File names across all commits are evidence for Stack and Concepts only — never state them in the output.

<input>
pusher: alopez-dev
repo: freelance-invoicer
commits: [
  {"message": "add PDF export for invoices", "added": ["export/pdf.py"], "removed": [], "modified": ["requirements.txt"]},
  {"message": "add email delivery via SendGrid", "added": ["delivery/email.py"], "removed": [], "modified": ["requirements.txt", "config.py"]},
  {"message": "queue exports so large invoices don't block the request", "added": ["tasks.py"], "removed": [], "modified": ["export/pdf.py"]},
  {"message": "retry failed sends up to three times", "added": [], "removed": [], "modified": ["delivery/email.py"]}
]
</input>
<output>
🧾 I just made my freelance-invoicer project deliver finished invoices straight to clients!

Invoices can now be exported as polished PDF documents rather than living only inside the app. Once generated, they're emailed directly to the client without the freelancer having to download and send anything by hand. Because generating a large invoice can take a moment, that work now happens in the background instead of making the user wait for the page to respond. And if an email fails to go out, the system automatically tries again a few times before giving up, so a temporary hiccup on the email provider's end doesn't quietly lose an invoice.

With this in place, sending a client their invoice is now a single action instead of a manual export-and-email routine.

Stack: Python · SendGrid
Concepts: Document Generation · Background Processing · Automatic Retries

Check out my project: github.com/alopez-dev/freelance-invoicer
</output>
</example>
